## Behavior and failure policy

The implementation saves the complete SES request in a private intake bucket **before** calling SES. If that save fails, it does not send the ordinary email and returns a definite pre-send failure. This adds a dependency on S3 availability and can delay ordinary delivery. This chosen exception to the plan's uninterrupted-delivery goal applies only when capture is enabled. Best-effort capture would permit delivery during a capture outage but could leave a permanent Sent gap; it is not implemented. Verification/reset delivery is unchanged.

After SES accepts a message, a failed status write does not turn success into failure or retry the email. Correlated SES feedback can resolve the missing acknowledgement. A provider timeout is recorded as uncertain; a definite provider rejection is failed. Existing producer handling of provider errors is preserved, including ExampleOrg learning mail's current failed result on timeout. Capture does not add an automatic provider retry. A stable attempt ID may be supplied by a producer; replay of the same reservation is refused without another SES call. The adapters generate a new capture ID for each existing SES invocation, so existing producer-level retry and idempotency behavior still applies.

A dedicated S3 → SQS → Lambda path imports the message once into its sender's Sent folder, already read, labelled automated and staging/production. It retains text, HTML, Reply-To, Bcc, inline parts and attachments. Raw SES MIME is retained byte-for-byte. For SES Simple messages the canonical complete request is retained as `producer.json`; display MIME is reconstructed, so it is not a claim to have SES's exact generated wire MIME. Capture records are limited to 48 MiB to fit the existing per-object backup bound.

A new captured sender receives a read-only mailbox. Existing alias receiving, sending and default settings are preserved. Captured mail produces no new-inbound notification. Delivery events cannot downgrade a delivered status to a late acceptance; source, account, configuration set and topic provenance are checked. Replayed imports preserve user folder changes, and permanent-deletion receipts prevent resurrection.

## Storage, infrastructure and operations

`infra/capture.mjs` defines a private encrypted, versioned intake bucket, dedicated encrypted queue/dead-letter queue and a worker with a restricted database role. Each enabled producer can write only its source prefix; it receives no mailbox read, list or delete access. Source identity determines domain/environment; submitted labels are not trusted.

Filed `producer.json` content follows existing mailbox deletion and backup/recovery rules. The intake is a temporary buffer: lifecycle expires current objects after 14 days and noncurrent versions after one day; an independent recovery-maintenance sweep physically removes every version aged 15 days or more. Cleanup depends on healthy hourly maintenance. This sweep must be configured before enabling producers. Failed imports retry and eventually enter the dead-letter queue; outage recovery must occur before buffer expiry.

The capture stack adds a destination to the website's existing SES configuration set. A separate staging feedback template adds a dedicated ExampleOrg capture topic/destination and authorizes the exact production capture queue subscription. Existing website metrics and ExampleOrg feedback destinations remain. Cross-account source permissions are exact-role and exact-prefix grants. All producer role parameters default empty; production ExampleOrg sending is never enabled by this template. Staging website and future production ExampleOrg feedback destinations need concrete configuration-set wiring before those sources are enabled.

Three alarms cover worker crashes, queue age over five minutes and dead letters, routed to the existing owner alarm topic. Normal synchronization within a few minutes remains a cloud acceptance check, not a measured local result. Additional running charges include three alarms, Lambda, SQS, S3 and SNS usage; the incremental bill has not been measured. SNS event topics retain the project's accepted standard, unencrypted metadata-topic configuration; full message content is stored privately in S3.
